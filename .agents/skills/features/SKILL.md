# The Goal

This mod aims to control individual letters triggered by in-game incidents (`IncidentDef`) in RimWorld. Rather than controlling generic letter categories (`LetterDef`), it controls the specific letters generated by each individual incident.

# Features

This mod consists of the following features:

- Mod settings screen for configuring letter handling behaviors per incident (`IncidentDef`).
- Incident execution context tracking to accurately associate arriving letters with their originating incident.
- Implementation to intercept and control letter display, sound, and game pause behavior based on configured settings.


# Mod UI Design

The UI design of this mod must respect RimWorld's native design aesthetics and conventions.


# Settings Screen

This mod shall be implemented so that the settings screen is accessible via
Options > Mod Options, both from the main menu and during gameplay.

## Requirements for the Settings Screen

- Keyword search to find specific incident letters by incident label, `defName`, or mod name.
- Filtering functionality to filter incidents by DLC or originating mod.
- A list of **all** incidents (`IncidentDef`) that send letters:
  - The list must support sorting by criteria such as title/label, mod, and configured behavior.
  - The list must include incidents added by mods in addition to vanilla and DLC incidents.
- The user must be able to select the following behaviors for letters generated by individual incidents in the list via a dropdown menu or similar UI element:
  - **Ignore**: The letter triggered by the target incident will not be displayed as an in-game letter, and no letter arrival sound will play.
  - **Default**: Respects vanilla behavior and the "Pause on Letter" game option.
  - **Pause**: Pauses the game immediately when the incident letter arrives, even if the letter is not a letter type covered by the "Pause on Letter" option.
- Reset button allowing the user to restore all incident letter behaviors to Default with a confirmation dialog.

## Settings Application Trigger

When settings are modified, the changes must take effect immediately without
requiring the game to be reloaded.


# Implementation Architecture

To control letters on a per-incident basis instead of by generic letter type (`LetterDef`), the implementation follows this architecture:

1. **Incident Cataloging (`IncidentItem` & `IncidentFilterService`)**:
   - Collects all incident definitions from `DefDatabase<IncidentDef>.AllDefsListForReading`.
   - Catalogs all valid incident definitions so players can control letters for both vanilla incidents (such as raids, trader visits, or resource crashes) and modded incidents (such as Dynamic Diplomacy) that dispatch letters dynamically from their worker classes.
   - Caches filtered and sorted results using dirty-flag tracking to guarantee $O(1)$ allocations on render frames.

2. **Incident Execution Context Tracking (`IncidentContext` & `IncidentWorkerPatch`)**:
   - RimWorld letters (`Verse.Letter`) do not intrinsically store references to the `IncidentDef` that generated them.
   - Maintain a thread-safe execution scope (`IncidentContext.CurrentIncident`) using Harmony prefix and postfix on `IncidentWorker.TryExecute(IncidentParms)`.
   - Use `__state` in the Harmony patch to safely preserve and restore context across nested or re-entrant incident executions.

3. **Letter Interception & Control (`LetterStackPatch`)**:
   - Hooks `Verse.LetterStack.ReceiveLetter(Letter, string, int, bool)`.
   - Queries `IncidentContext.CurrentIncident` to determine the originating incident.
   - If an incident context is active and has a configured behavior:
     - `Ignore`: Harmony prefix returns `false` to skip execution, suppressing the letter and its sound completely.
     - `Pause`: Harmony postfix executes `Find.TickManager.Pause()` if the letter was displayed and not delayed.
     - `Default`: Allows normal vanilla handling.
   - If no incident context is active (e.g. player actions, quests, or non-incident letters), standard processing continues unmodified.

4. **Settings Persistence & Computational Complexity**:
   - Configured behaviors are stored in a dictionary keyed by `IncidentDef.defName` with case-insensitive matching, ensuring $O(1)$ lookup time complexity.
   - Entries with `LetterBehavior.Default` are omitted from serialization to optimize space complexity ($O(K)$ where $K$ is the number of customized incidents).
   - Strictly adhere to the General Skill Rules (SOLID principles, clean architecture, automated testing).
